# PRD: Visual Input / Output Blocks for Swarm Workflows

- Implementation style: **node-first UX / graph-first semantics, contract-backed MVP**

## Requirements Summary

The Swarm workflow canvas must make inputs, per-agent outputs, and artifacts visible and connectable as part of the graph. The user should no longer need to define workflow inputs/outputs primarily from Settings. Instead, the canvas should become the primary design surface:

- Input blocks collect structured user input at workflow start and inject it into connected agents.
- Input blocks can be multiple and may contain mixed structured fields, including text + image upload fields.
- Agent-level output configuration defines what each agent is expected to pass downstream.
- Output Extractor blocks consume upstream agent output and create typed artifacts.
- MVP reuses current `inputContract` / `outputContract` runtime infrastructure as an internal bridge while node graph becomes the user-facing source of interaction.

## RALPLAN-DR Summary

### Principles

1. **Canvas is the user-facing source of truth.** Users define workflow I/O by placing and connecting nodes, not by editing hidden Settings rows.
2. **Contract-backed, not contract-led.** Reuse `inputContract` / `outputContract`, but derive/sync them from node definitions.
3. **Component-by-component execution.** Build in macro-waves with microwave deliverables so each component can be tested independently.
4. **Compatibility before replacement.** Existing workflows must keep loading and running.
5. **Structured reliability over full context control.** MVP improves scoped I/O contracts without building a full memory manager.

### Decision Drivers

1. Reliability of agent handoffs.
2. Implementation safety through reuse of current run/result/artifact infrastructure.
3. Future extensibility for richer artifacts and pack integration.

### Viable Options

- **Option A — Settings-first compatibility patch:** lowest risk, but rejected because it keeps I/O as hidden metadata and fails graph-first scenarios.
- **Option B — Node-first UI with contract-backed bridge (chosen):** aligns with user intent, preserves infrastructure, supports incremental waves; requires source-of-truth discipline.
- **Option C — Full node-native runtime rewrite:** clean long-term model, but deferred because it is too risky and broad for MVP.

## ADR

**Decision:** Implement Visual Input / Output Blocks as a node-first, contract-backed MVP.

**Drivers:** connectable blocks and per-agent control; existing contract infrastructure already supports run forms/results; MVP must support text+image inputs, per-agent output expectations, and Output Extractor artifacts without becoming a total context manager.

**Alternatives considered:** Settings-first visual summaries (rejected: product mismatch); full node-native rewrite (deferred: high risk and migration cost).

**Why chosen:** It lets the team go deep component-by-component while preserving a safe technical spine.

**Consequences:** Need a contract derivation layer; Settings Interface must stop being the primary edit surface; tests must cover node behavior and bridge behavior.

**Follow-ups:** full node-native runtime, richer media/file artifacts, and pack builder mapping after MVP.

## Architect Consensus Revisions Applied

### R1 — Non-executable graph semantics

Input and Output Extractor nodes are **non-executable graph nodes** in the MVP.

- `input` nodes run during **workflow preparation**, not as agent sessions.
- `outputExtractor` nodes run during **result/artifact assembly**, not as agent sessions.
- Start-agent detection must ignore incoming edges from `input` nodes so `Input -> Agent` does not make the agent non-startable.
- Runtime scheduling must not spawn PTY/stream-json sessions for Input or Output Extractor nodes.
- Valid MVP edge types:
  - `input -> agent`
  - `agent -> agent`
  - `agent -> outputExtractor`
  - optionally `agent -> flowControl` and existing flow-control edges unchanged.
- Invalid or warning edge types:
  - `input -> outputExtractor` is invalid unless a future transform node is introduced.
  - `outputExtractor -> agent` is invalid in MVP; extractors terminate artifact paths.
  - `input -> input` and `outputExtractor -> outputExtractor` are invalid.

Add explicit microwave **MW1.5 Graph execution semantics** before visual runtime integration.

### R2 — Effective MVP data schemas

#### `InputNode.data`

```js
{
  label: 'Client Brief',
  description: 'Brief shown in canvas/inspector',
  prompt: 'Question shown to the operator at run start',
  submitMode: 'runStart', // MVP; later: midFlow
  outputFormat: 'json',   // json | markdown
  fields: [
    {
      id: 'field-brief',
      key: 'brief',
      label: 'Brief',
      type: 'textarea', // text | textarea | markdown | json | enum | number | integer | boolean | image
      required: true,
      defaultValue: '',
      helpText: 'Paste the client brief',
      options: []
    }
  ]
}
```

#### Image input value shape

```js
{
  assetId: 'run-asset-id',
  name: 'reference.png',
  mimeType: 'image/png',
  size: 123456,
  previewUrl: '/api/v1/swarm/assets/run-asset-id/preview'
}
```

Prompt injection should include metadata/reference and an explicit note that the image is attached/available by reference. Raw base64 must not be injected by default.

#### `AgentNode.data.expectedOutputContract`

```js
{
  format: 'markdown', // text | markdown | json
  instructions: 'Return a concise implementation plan with sections...',
  schema: null
}
```

Existing `data.expectedOutput` remains a legacy/free-text fallback and can be migrated into `expectedOutputContract.instructions`.

#### `OutputExtractorNode.data`

```js
{
  label: 'Final Report',
  artifactKey: 'final-report',
  artifactName: 'Final report',
  format: 'markdown', // markdown | text | json | table
  instruction: 'Extract the final report from the upstream agent output.',
  sourcePolicy: 'allIncoming', // firstIncoming | allIncoming | selected
  selectedSourceNodeIds: []
}
```

`table` is an MVP artifact format in the node model; internally it may serialize as JSON/CSV-like text for existing artifact rendering until a dedicated table viewer exists.

### R3 — Image upload / run asset boundary

MVP should use a controlled **run asset upload** boundary:

- Uploads are tied to a pending run/session input, not arbitrary project mutation.
- Uploaded images are stored as run-scoped assets or controlled temp assets.
- Workflow input payload references assets by metadata/reference shape, not raw base64 by default.
- Allowed MIME types initially: `image/png`, `image/jpeg`, `image/webp`, `image/gif` if safe.
- Size limit must be explicit in implementation; recommended MVP cap: 10 MB per image and small total run cap.
- Server must reject traversal filenames and unsafe paths.
- Server must not expose arbitrary project filesystem reads.
- Prompt logs must not include full image content.

If implementation cannot safely add upload storage in the first pass, fallback is an explicit blocked state: image input UI can be designed, but execution must reject image fields until upload route exists. Do not silently drop image fields.

### R4 — Output Extractor dataflow contract

- One Output Extractor node produces one artifact.
- Extractor source nodes are resolved from incoming `agent -> outputExtractor` edges unless `sourcePolicy: selected` is configured.
- `firstIncoming` uses deterministic edge order by workflow edge order.
- `allIncoming` concatenates/lists upstream agent outputs with labels.
- `selected` uses `selectedSourceNodeIds` and must validate those IDs are connected or reachable.
- Missing upstream output yields artifact status `empty` or `error`; it must not silently fall back to unrelated aggregate final text.
- Artifact result should carry extractor provenance where possible: `{ extractorNodeId, sourceNodeIds, sourcePolicy }`.

### R5 — Settings Interface policy

- For workflows with visual Input/Output Extractor nodes, Settings Interface must be **read-only summary or advanced legacy view**, not an editable competing source.
- For legacy workflows with no visual I/O nodes, old contract editing may remain available as fallback until migration exists.
- If migration is added, it must be non-destructive and user-visible.
- The app must avoid dual editable sources of truth.

## Mandatory Wave Quality Gates — Added by Ralplan Refinement

This refinement is binding for execution: **no macro wave and no microwave may be marked complete, merged into the next wave, or used as a downstream dependency until its tests pass and its relationship with the current system is verified against a specific expected result.**

### Universal Done Definition for Every Microwave

Each microwave must finish with a short evidence block containing:

1. **Client test evidence** — exact command(s), pass/fail result, and affected UI behavior. If no direct client surface exists, state `Client: N/A` with rationale and run the nearest client regression that proves no visible regression.
2. **Server test evidence** — exact command(s), pass/fail result, and affected API/runtime behavior. If no direct server surface exists, state `Server: N/A` with rationale and run the nearest server regression that proves no backend/runtime regression.
3. **Current-system relationship test** — an explicit integration/regression check proving the new element still works with today’s existing workflow system.
4. **Specific expected result** — not “works”; a concrete assertion such as “legacy workflow with `inputContract` still opens the run modal with one textarea field” or “Input -> Agent does not prevent the agent from being detected as a start agent.”
5. **Blocking rule** — if any required test fails, stop the wave, fix or re-plan, and do not proceed to the next microwave/wave.

### Universal Done Definition for Every Macro Wave

Each macro wave must finish with:

- all microwave gates passed;
- one client-side wave regression suite passed;
- one server-side wave regression suite passed;
- one current-system compatibility check passed;
- updated evidence notes in implementation progress/memory;
- explicit list of remaining risks before unlocking the next wave.

## Advancement Rule

The implementation lead must treat each microwave as a gated checkpoint:

```txt
Implement microwave -> run client tests -> run server tests -> run current-system relationship test -> record specific expected result -> only then continue.
```

If a test is not applicable for a microwave, the executor must replace it with the closest regression proving that layer did not break and explicitly document why the direct test is N/A.

## Gate Policy Revision 2 — Superseding Execution Rule

This section supersedes any earlier ambiguous wording about “always run client and server tests.” The binding rule is stricter and more precise:

For **every microwave**, both client and server impact must be classified as one of:

- **Direct test** — the layer was changed or directly affected; relevant tests must be created/extended and pass.
- **Substitute regression** — the layer was not directly changed, but nearby integration must be protected; the closest regression test must pass.
- **N/A with rationale** — no meaningful layer relationship exists; rationale must be recorded.

A microwave may proceed only when all Direct/Substitute tests pass and all N/A rationales are recorded.

### Baseline Gate Policy

- Affected baseline tests must pass before Wave 1.
- If affected baseline tests fail, create/fix a baseline-stabilization microwave before feature work unless the failure is proven unrelated and recorded as pre-existing.
- No wave may introduce new failures relative to the recorded baseline.
- Any pre-existing exception must include command, failing test name, suspected owner, and why it does not invalidate the next wave.

### Automation-first Relationship Checks

Current-system relationship tests should be automated whenever reachable through existing unit/integration/E2E harnesses. Manual checks are allowed only for visual inspection gaps and must include exact steps, observed result, and why automation was not practical.
